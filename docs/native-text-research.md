# Native text conversion and window transfer research — 2026-10-08

Version 0.1.10 removed all conversion-path clipboard access and Copy/Paste commands. Version 0.1.11 added native replacement in the proven Spotlight search field, including a narrowly scoped plain-query value setter. Version 0.1.14 completes either input mode with the exact empty caret at the replacement's end, removing automatic result selection. Other editors retain fresh coherent Accessibility evidence, proven selected-text setters and prebuilt Unicode events. Earlier native, Figma and Spotlight live fixtures are versioned historical evidence below and in validation.md; they do not assert the old selection-retention behavior for 0.1.14.

## What the public macOS interfaces provide

| Interface | Supported operation | Constraint for SSwitcher |
| --- | --- | --- |
| Accessibility selected text, value and selected range | Read a participating application's text and selection. A settable selected range can restore a selection. | The application supplies the data. Slots may be missing or inconsistent; a successful setter is not proof of a visible edit. |
| `CGEvent.keyboardSetUnicodeString` | Embed a finished Unicode string in a keyboard event. | Apple warns that application frameworks can ignore that string and translate the virtual key themselves. Queue receipt is separate from editor acknowledgement. |
| `NSTextInputClient.insertText` | Insert text into the receiving text view, replacing a specified range. | This is a method on a participating `NSView`/`NSTextView` receiver, not an API that gives a menu-bar utility an arbitrary other-process text view. |
| InputMethodKit | Supply text through client sessions belonging to an input method. | A custom input method receives a real client session. Adopting this would require a separate installed input method and user selection of it, rather than providing a global editing client for the current utility. |
| Accessibility text markers | Represent and navigate positions and selections in an engine that implements them. | Marker bytes belong to the target engine and are opaque to assistive clients. They provide richer position/read operations, not a universal text replacement transaction. |
| macOS Services | Exchange input and output data with a service provider. | `NSPerformService` requires the caller to supply a pasteboard already containing the service's input. It does not fetch and replace any arbitrary focused selection. |

The distinction between in-process text views, input-method client sessions and external Accessibility objects follows from the documented receiver/session contracts. The conclusion that none gives this utility universal confirmed replacement is an architectural inference, not an Apple promise about every application.

The local macOS SDK confirms `AXSelectedText`, `AXSelectedTextRange`, `AXSelectedTextRanges`, `AXNumberOfCharacters` and parameterized `AXStringForRange`. Its `AXWebConstants.h` documents text-marker indices as UTF-16 units and marker payloads as engine-owned opaque positions. The current SDK's marker declarations do not by themselves establish compatibility with the application's macOS 13 baseline.

## Caramba and other macOS implementations

The [Caramba official site](https://caramba-switcher.com/en/) describes automatic conversion and double-Shift undo. It also states that it cannot work or disable itself correctly in every application/browser window, and that RDP is unsupported. The [official secure-input help](https://caramba-switcher.com/help/secure-input/) explains the restriction when another application enables secure input. The inspected official pages do not document Caramba's selected-text transport or claim that it never touches the clipboard. Live observation can establish its behavior in a fixture; it cannot establish its internal algorithm. Historic press excerpts on the site are not sufficient evidence of the current Mac version's shortcuts.

[UASwitcher's source](https://github.com/deimoc/UASwitcher/blob/main/Sources/UASwitcher/TextConverter.swift) uses Unicode events for a word accumulated from typed keys. Its selected-text path falls back to `convertViaClipboard`, issues Copy and Paste, and schedules clipboard restoration. Its README's “clipboard-free” description therefore does not apply to every selected-text conversion. Its timed clipboard fallback would preserve the dependency that this change intends to remove.

[Traple's SelectionService](https://github.com/spendolas/traple/blob/main/Sources/SelectionService.swift) reads `AXSelectedText` and replaces it through the same attribute. Its comment warns that Electron/web inputs can silently fail. The function treats a successful setter return as success without checking the resulting document or selected range. SSwitcher's earlier independent Figma probe already found that exact failure: a reported successful setter did not change the visible canvas or actual copied characters. That method is unsuitable for the tested Figma editor.

[AutoSwitcher](https://github.com/emkaraid/AutoSwitcher) explicitly documents its selected-text conversion through the clipboard with restoration. Its README places the event tap on the main run loop and marks its generated events. SSwitcher already uses a main-run-loop listening tap and distinct synthetic delivery markers. These architectural choices do not supply a clipboard-independent external selection transaction.

A scoped native NSTextView comparison of installed Caramba 2026.09.22 converted the 17-UTF-16-unit fixture `ghbdtn vbh 🙂 é\n` to Russian. The observed events included Command+C and Command+V from Caramba's process. Pasteboard revision changed from 1911 to 1915 across five observed revisions, then all readable formats/data matched the original snapshot. The resulting selection was a caret at offset 17, so the selected fragment was not retained in this fixture. A subsequent unselected-caret gesture left the fixture unchanged and issued only Copy. This is black-box fixture evidence, not a claim about every Caramba path or its internal code. Reading lazy pasteboard providers can trigger their data provision; concurrent clipboard managers can also affect revision observations.

These projects demonstrate usable public mechanisms and their tradeoffs. Their source comments and README claims are not compatibility measurements for SSwitcher.

## Implemented clipboard-independent path

1. Read the current editable text element and a coherent document/range/selected-text snapshot. Validate UTF-16 bounds and whole grapheme boundaries. When an attribute is supplied, it must agree exactly, including its UTF-16 representation. Refuse missing, inconsistent or noncontiguous scope before editing.
2. Prepare the finished replacement before reserving the attempt's one mutation. A fresh settable AXSelectedText query permits one selected-fragment setter only in tested TextEdit/own NSTextView and the proven Spotlight search field; other editors use all prebuilt immutable Unicode events. Ordinary word mode retains Backspace + Unicode input. Spotlight's plain-query word setter is the explicit exception described below. Recheck the same focus, input generation, document and range immediately before mutation.
3. Pace the existing keyboard transport through delivery receipts while preserving modifier waits, cancellation and the burst guard. Do not use Copy, Paste, cut, clipboard probes or clipboard restoration.
4. Within one fixed deadline, require the exact expected document and empty caret at the replaced fragment's UTF-16 end. Every supplied selected-text/ranges attribute must agree with that empty caret. Finish immediately on proof, without a result-selection setter, Command+A or arrow walk. Never use Figma's false-success text/value setters.
5. An unverified edit must stop further events and must not trigger another mutation or clipboard fallback. Only Spotlight's plain-query word path may correct an already empty relocated caret once, under its original deadline; ordinary selected replacement has no extra selection phase.

A read-only Figma fixture established an actual 21-unit document containing hard LF, consecutive LF and U+2028, while AXValue reported 23 units. AXStringForRange(0,21) returned the exact physical 21 units; (21,0) returned an empty string; (21,1), (0,22) and (0,23) returned explicit NoValue (-25212). Prefix (0,20) and partial (7,3) also returned exact physical characters. Start/end text markers were available but both indices returned zero, so they are excluded from extent proof.

The scoped canonical provider obtains the document through that public range API and proves its endpoint within fixed time/query bounds. It checks exact repeated strings and fresh unchanged raw evidence, never strips LF or treats a generic nil/IPC failure as an endpoint. Only this demonstrated Figma editor may interpret NoValue as a range bound. Other unsupported/inconsistent cases are refused before editing. Independent 0.1.10 review passed whole, partial and word roundtrips on the 21-unit hard/consecutive/soft-line fixture. A separate 22-unit emoji/decomposed-accent multiline fixture passed whole conversion and exactly one reverse conversion during a 40-tap Shift burst, with exact final text and the then-retained selection. These are scoped historical Figma observations, not a universal AXStringForRange or line-key contract.

## Spotlight on the tested macOS 27 host

Apple's [macOS 27 Spotlight guide](https://support.apple.com/en-in/guide/mac-help/mchlp1008/27/mac/27) documents Spotlight integration with Siri AI when enabled. It does not specify process names or promise a particular AX tree. Read-only host inspection found the legacy Spotlight launch agent disabled and the active UI hosted by `com.apple.campo`. Opening Spotlight exposed a search system dialog, while NSWorkspace continued to report Finder. Public system-wide Accessibility reported Campo as both focused application and focused field owner.

The actual search field was AXTextField/AXSearchField with identifier `SpotlightSearchField`, under AXWindow/AXSystemDialog. A fixture double Shift on 0.1.10 left `ghbdtn` unchanged and emitted no SSwitcher input: the existing target/frontmost guard cancelled before mutation. Thus the earlier unverified Spotlight check had observed the wrong focus source; it had not established that Spotlight failed to open.

During the 0.1.11 investigation, one fixture-only AXSelectedText write converted selected `ghbdtn` to `привет` in 3.43 ms, and a separate reverse write took 10.42 ms. Both reported success and were followed by exact full document/caret readback and unchanged global field identity. These observations justify a selected-fragment backend only for the proven search field, with fresh native capability checks and exact result acknowledgement. They do not establish support for Siri conversation inputs or other Campo windows.

Version 0.1.11 introduced preservation of the initial background foreground PID and public global owner plus original field/window proof before mutation, acknowledgement and range writes. These guards remain in 0.1.14; ordinary target mismatches remain refused. An integrated keyboard word test left `gпривет` after six Backspace pairs and one Unicode pair: the search field dropped one deletion during query updates. The native correction therefore rejects all keyboard fallbacks in the verified Spotlight field.

Fixture-only AXValue probes proved `ghbdtn` ↔ `привет` with exact caret 6/0 (7.89/6.28 ms), and the first word of `ghbdtn ghbdtn` with its suffix preserved (5.39 ms). The latter value setter moved the caret from 6 to 13. Separate roundtrips then proved one zero-length range setter restores caret 6/0 without selecting the word (0.70/1.23 ms), after exact result-document, empty current caret and global field/window proof. Clipboard revision 1917 and readable formats/data stayed unchanged.

Only that proven plain single-line query permits a complete AXValue write in production. The word transport rederives the exact one-word result at the original caret, requires fresh value/range capabilities, writes once, then acknowledges the document before one optional native caret correction and final exact readback within the original deadline. In 0.1.14, selected mode keeps one AXSelectedText setter and the native-range capability guard, then confirms the empty end caret without restoring a selection. Missing capabilities refuse before mutation; neither mode retries, clears an unexpected selection or falls back to Unicode. Other editors retain the selected-fragment/keyboard policy and receive no full-value writes. No clipboard or submit keys enter either path. The SDK's NSWorkspace foreground description is insufficient to authorize this observed overlay alone; the narrow global AX policy follows from the independently measured focus evidence.

Independent 0.1.11 final-candidate fixtures passed whole-word, whole-selection, first-word-with-suffix and partial-selection roundtrips. Inside-word/after-space attempts left the query unchanged. A 40-tap burst produced exactly one native conversion, confirmed in 191 ms with exact caret 6/0 and no selection. All observers retained the same global field/window/background, unchanged clipboard revision/formats/data and zero SSwitcher keyboard events. That version's 118 tests passed locally and independently. These establish compatibility with this actual search field on the tested macOS 27.0.1 host, not every OS version or Campo input, and predate 0.1.14's selected-result behavior.

## Empty-caret completion — 0.1.14

The existing first acknowledgement already proved the complete replacement document and a valid empty caret at the fragment's exact UTF-16 end. Previously, selected mode then selected the result through a native range setter or Figma keyboard walk. The new default ends at that first proof for both modes. It removes the restoration transport and its second acknowledgement phase while retaining original input selection, grapheme boundaries, unchanged prefix/suffix, editability, focus, secure-input, cancellation and timing guards.

The next gesture uses a fresh snapshot and ordinary word eligibility at the actual caret. It has no previous-selection history and does not automatically reverse an entire former selection. Spotlight word-value replacement keeps its one zero-length correction for a relocated empty caret, with fresh proof and worker-side original-deadline checks. A retained highlight or changed document never confirms success and is not cleared by a fallback mutation. New core regressions exercise full/partial/multiline replacement, repeated neighbors, emoji and decomposed Unicode, continuation at the fragment's end and rejection of highlighted/contradictory evidence. Live evidence for this version is recorded separately in validation.md.

## Branded Electron packages and duplicate launches — 0.1.12

The installed ChatGPT package has `Codex Framework.framework` instead of `Electron Framework.framework`, plus a documented `ElectronAsarIntegrity` entry and an actual `Resources/app.asar`. Its framework is a versioned FMWK package with a real executable. The old framework-path detector classified it as non-Electron, skipping the existing manual-accessibility preparation. In the user's 0.1.11 test, diagnostics reported no accessible editor snapshot and zero synthetic keyboard events while permissions and the listening tap worked. This establishes an early refusal and a concrete package-recognition defect; it does not identify the precise failing AX attribute inside the protected application.

Electron's [accessibility guide](https://github.com/electron/electron/blob/main/docs/tutorial/accessibility.md) documents third-party `AXManualAccessibility` activation on macOS, and its [ASAR integrity guide](https://www.electronjs.org/docs/latest/tutorial/asar-integrity) documents the package metadata. Version 0.1.12 recognizes that metadata only with the corresponding archive file and actual framework package/executable, preserving standard framework paths and versioned symlinks. It reads no archive contents and grants no app-name exception to focus, editability, text or selection proof. Successful tree activation still requires fresh coherent editor evidence; unavailable snapshots are not blindly retried.

Two copies of 0.1.11 were also observed running from the workspace and `/Applications`. Version 0.1.12 acquires a process-lifetime nonblocking file lock before AppKit UI, observers or the event tap. Apple's [runningApplications(withBundleIdentifier:)](https://developer.apple.com/documentation/appkit/nsrunningapplication/runningapplications(withbundleidentifier:)) provides the additional startup check for an already running older copy. That snapshot cannot make an unmodified older version obey the new lock if it launches concurrently or later. No other process is terminated or activated. The installed 0.1.12 retained one process when another copy was explicitly launched.

The user subsequently reported that conversion appeared to work everywhere they checked, confirming the requested ChatGPT fix manually on the installed 0.1.12. This is a user report, not an automated AX trace, exhaustive application matrix or completed-frame measurement. Computer-use access to the actual `com.openai.codex` application was prohibited; no AX, AppleScript or keyboard helper bypass was used.

## Window transfer and Windows behavior — 0.1.13

Microsoft's [Windows shortcut reference](https://support.microsoft.com/en-au/accessibility/windows/keyboard-shortcuts-in-windows) documents Win+Shift+Left/Right as moving the active window to the monitor on that side. Win+Shift+Up stretches a desktop window vertically; Down restores a snapped/maximized window, with vertical restore/minimize behavior described for Windows 10. SSwitcher's four physical directions, including Up/Down, are an explicit extension chosen by the user. No Windows machine was live-tested here, and the shortcut reference does not specify the Shell's exact normal-frame remapping, snap restoration or monitor ordering.

Microsoft's [multiple-monitor positioning guide](https://learn.microsoft.com/en-us/windows/win32/gdi/positioning-objects-on-multiple-display-monitors) describes largest-intersection monitor selection and distinguishes maximized work-area bounds from fullscreen display bounds. Its [WM_DPICHANGED contract](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged) supplies a DPI-scaled suggested rectangle to a participating application. [WINDOWPLACEMENT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-windowplacement) stores normal placement and show state. These contracts do not prove the Shell shortcut's implementation or unchanged pixel dimensions on every app/DPI transition.

On macOS, [NSScreen.screens](https://developer.apple.com/documentation/appkit/nsscreen/screens) supplies the current layout, and [visibleFrame](https://developer.apple.com/documentation/appkit/nsscreen/visibleframe) supplies the work area. The local public SDK's `AXAttributeConstants.h` defines AXPosition as global top-left point coordinates and AXSize in points. AppKit rectangles use the primary screen's [bottom-left coordinate system in points](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CocoaDrawingGuide/Transforms/Transforms.html), so the conversion flips Y around the primary frame's top edge. Backing scale is not applied to window sizes. Current screens are reread per transfer and guarded with screen-change notifications; no layout setting is changed or idle display polling added.

The selected macOS policy preserves an ordinary window's point size and relative placement in available work area, with a permitted shrink to fit. Explicit full/half/quarter geometry maps to the corresponding work-area fraction. This is a geometry heuristic with a two-point tolerance, not a native zoom/snap-state API or exact Windows emulation. There is no saved-normal-frame history: a large ordinary window fitted to the entire smaller work area is subsequently recognized as filled. Fixed-size windows refuse any required resize. Fullscreen Spaces are unsupported; known fullscreen state and unknown full-display-sized frames are conservatively refused, without private Spaces APIs or automatic fullscreen exit.

The public `CarbonEvents.h` declares global hotkeys, exclusive registration, pressed/released events and unregistering, with main-thread use because registration is not thread-safe. Apple's [Frameworks Engineer clarification](https://developer.apple.com/forums/thread/763878) explains the Option/Option+Shift refusal introduced in macOS 15.0 and the change in 15.2 Beta 2. A temporary register/immediately-unregister probe on this macOS 27.0.1 host returned OSStatus 0 for all four exclusive Option+Shift+arrows; it sent no keyboard events and accessed no external AX objects. Product registration still checks each result and rolls back partial success. The existing conversion tap remains listen-only. Disabling the separate window feature unregisters all four combinations so their ordinary text-selection behavior can return.

The installed 0.1.13's human physical Down/Up trial was confirmed by the user as “Да, переносится туда и обратно”. That is a manual direction/roundtrip report on this Mac; it does not establish exact post-transfer bounds, native Windows equivalence, different-scale display behavior or every application. An app-bound CUA key action did not produce an observed global-hotkey transfer and was not counted as a physical shortcut test. Additional fixture evidence is recorded separately in validation.md.
